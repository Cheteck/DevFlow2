# Session Report — 2026-11-05

## Objectif
Corriger le système de thème MosaiX (P0: validation centralisée, P1: thread-safety SSR)

## Travaux réalisés

### P0 — Centralisation de la validation
**Fichier:** `packages/theme/src/theme-discovery.ts`

- `ThemeManifestSchema` de `@mosaix/schemas` est maintenant le **seul point d'entrée** pour la validation des manifestes de thème (plus de regex inline, plus de duplication)
- `ThemeValidationError` vient de `@mosaix/theme` (hiérarchie d'erreur existante)
- Invariant `folder name === manifest id` conservé comme vérification post-valeurs
- `packages/theme/src/theme-manifest-schema.ts` **supprimé** (schéma dupliqué)

### P1 — Bridge thread-safe
**Fichier:** `src/shell/theme/theme-bridge.ts`

 État supprimé (cause racine de la contamination SSR) :
- `activeThemeId` — globale mutable
- `catalogLoaded` — globale mutable  
- `compiledForThemeId` — globale mutable
- `activeRuntime` — singleton mais accédé via globale

 État nouveau (ALS, par requête) :
- `themeStateStorage` (AsyncLocalStorage) — isolation complète entre requêtes
- `getEffectiveThemeId()` lit **uniquement** depuis ALS — aucun fallback vers globale
- Catalogue gelé après boot (`Object.freeze`) — partagé-sécurisé
- `ThemeRuntime` stateless, partagé ; toute la state vit dans ALS
- `setActiveThemeId()` ne fait que valider (la theme est définie via `runWithThemeContext`)

## Décisions prises
1. **`ThemeManifestSchema`** canonique = celui de `@mosaix/schemas` (zod, `.passthrough()`, tokens optionnel)  
2. **`runWithThemeContext`** est le seul moyen de définir la theme ID par requête  
3. `setActiveThemeId()` devient une validation pure, pas une mutation d'état  
4. Le catalogue est immuable après initialisation — plus de `catalogLoaded`
