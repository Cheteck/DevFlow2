# Session 2026-11-11 — `@mosaix/migrations` : migrations TypeScript natives exclusively

## Objectif

Finaliser le package `@mosaix/migrations` : le moteur n'accepte **plus que** des
migrations TypeScript natives. La règle (« aucun SQL brut dans une migration »)
est inscrite **dans le code**, pas seulement documentée. Travail mené en
collaboration étroite avec ChatGPT (revue d'architecture, arbitrages D1/D2/D3,
GO définitif).

## Travaux réalisés

### Le contrat, dans le code

`packages/migrations/src/migration.ts` :

```ts
export const LEGACY_SQL_FIELDS = [
  "content", "down", "kind", "rawSql", "downRawSql",
] as const;

export function assertTypeScriptNativeMigration(candidate, migrationId): void
```

Appliqué à **trois niveaux** (une migration SQL est rejetée avant toute
compilation ou exécution) :

| Niveau | Point d'entrée |
|---|---|
| `MigrationRegistry.register()` | `loadMigration()` (`registry.ts:57`) |
| `MigrationValidator.validate()` | `validator.ts:175` |
| `MigrationCompiler.compileUpAsync()` / `compileDownAsync()` | `compiler.ts:114/143/162` |

Le champ `raw()` (équivalent Laravel `DB::raw()`) a été **supprimé de l'API** :
il réintroduisait une porte d'entrée SQL libre. Ses 6 usages ont migré vers
`func("now")`.

### Le DSL

- `SchemaBuilder` : 22 blueprints (tables, index, schémas, contraintes,
  `ALTER COLUMN`, fonctions, triggers).
- `context.data` : `insert`, `insertSelect`, `update`, `delete`.
- Modèle d'expressions fermé et structuré ; une seule notion de requête
  (`select` / `subquery`).
- `createFunction(name, definition: TrustedFunctionBody, opts)` : **unique
  exception assumée** — un corps PL/pgSQL (du code de fonction), jamais une
  commande SQL. Typé, documenté, PostgreSQL uniquement.

### Conversion des migrations

**46 migrations** converties au DSL TypeScript, **0 portant du SQL**. Le
moteur compile les blueprints ; le Planner est la frontière de compilation (le
plan porte le SQL compilé : preview == exécution) ; le Runner n'exécute que
`op.statements`.

### Garde-fous (nouveaux, dans le dépôt)

`scripts/migrations/` — quatre audits comparant les migrations à leur
référence historique (`git HEAD`), à brancher en CI :

| Commande | Garantit |
|---|---|
| `pnpm audit:migrations` | les quatre audits ci-dessous |
| `audit-nullability` | une colonne historiquement nullable l'est toujours |
| `audit-types` | les types de colonnes n'ont pas dérivé |
| `audit-tables` | les références de table sont des noms, pas des fragments SQL |
| `audit-sql-equivalence` | le SQL généré est sémantiquement identique |

## Bugs réels trouvés et corrigés

Trouvés par la **vérification** (comparateur SQL + audits), pas par la relecture :

1. **27 colonnes** historiquement nullables rendues `NOT NULL` — schéma plus strict que la base déployée (INSERT refusé).
2. **6 références de table corrompues** (`data.update("UPDATE schema.table", …)`) — erreur à l'exécution.
3. `ADD COLUMN "capacity" INTEGER DEFAULT 1` rendu `TEXT` — type **et** default perdus.
4. `isNull` / `isNotNull` **inversés** dans 2 migrations — condition inversée.
5. Regex sur-échappée (`^\\d` au lieu de `^\d`) — aucun motif ne matchait.
6. `ALTER COLUMN … TYPE VARCHAR(255)` rendu `TEXT` dans le rollback — le rollback ne restaurait pas le type.
7. `REFERENCES "vendables"` sans le schéma — FK vers une table inexistante.
8. `DEFAULT '[]'` perdu sur `auditTrail`.
9. `TIMESTAMP` rendu `TIMESTAMP WITH TIME ZONE`.
10. Rollback dupliqué sur la migration citadelle (pas de `down` historique) — le rollback **re-créait** les tables.

## Risques détectés

- Les 3 audits comparent à `git HEAD` : **à rejouer après chaque modification
  d'une migration**, sinon la référence n'est plus l'historique converti.
- `createFunction` reste une exception : un corps PL/pgSQL est du texte. Il
  est typé et PostgreSQL-only, mais c'est la seule surface non structurée.
- Les checksums source change à chaque édition : `pnpm migration:checksums`
  doit suivre toute modification de migration.

### Découpage retenu

Un commit par famille plutôt qu'un commit unique : le moteur (la suppression
de `rawSql` et le nouveau DSL) est la partie qui doit être relue attentivement ;
l'enterrer avec 46 migrations la rend illisible. Les commits intermédiaires
sont rouges (`tsc` échoue tant que les applications ne sont pas converties) :
la branche n'est fusionnable qu'après le commit des applications.

### Note sur les tests d'isolation PostgreSQL

Les tests `*-pg-isolation.test.ts` et `portfolio-multi-tenant.test.ts` sont
**flaky** : ils créent et suppriment les mêmes schémas dans une base
PostgreSQL partagée. Ils passent isolément et échouent en parallèle
(`duplicate key value violates unique constraint "pg_type_typname_nsp_index"`).
Ces fichiers et leur helper `src/test/e2e-test-helpers.ts` sont
byte-identiques à la révision `8507d6d` : mes commits ne les touchent pas.
Le nombre d'échecs de la suite complète oscille donc entre 23 et 25 selon le
plan de parallélisation — c'est une dette de l'infrastructure de test, à
traiter dans un chantier dédié (base par fichier de test, ou
`--pool=forks --poolOptions.forks.singleFork`).
