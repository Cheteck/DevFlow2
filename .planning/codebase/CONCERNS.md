# Codebase Concerns

**Analysis Date:** 2026-08-08

## Tech Debt

### Capability I/O schema validation is a no-op (ARCH-011, still open)

- Issue: `validateCapability()` in `packages/core/src/capability-registry.ts:98-102` always returns `true` and discards input. `kernel.register()` seeds every declared capability with `entry: ""`, `permissions: []` and an empty `schema: {}` (`packages/core/src/kernel.ts:320-336`), and manifest operations reference I/O schema ids (e.g. `input: "identity.user.create.in"` in `apps/identity/src/index.ts:64-67`) that are never resolved or enforced.
- Impact: Any caller can pass unstructured/corrupt data through the capability boundary; capability I/O contracts are decorative.
- Fix approach: Implement I/O validation at `executeCapability` call time using `@mosaix/schemas` (backlog item T-A5), and have `register()` carry real schema references.

### Kernel observability hardcoded, not injectable (ARCH-010, still open)

- Issue: `packages/core/src/kernel.ts:147-149` instantiates `new ConsoleLogger(...)`, `new InMemoryMetrics()`, `new InMemoryTracer()` unconditionally; `KernelOptions` does not accept logger/metrics/tracer.
- Impact: OTel/production observability (adapters `logger-pino`, `metrics-otel`, `tracing-otel`) cannot be plugged in without modifying the kernel (violates ADR-0002 "never modify the kernel").
- Fix approach: Accept optional logger/metrics/tracer in `KernelOptions` with the in-memory defaults retained (backlog T-A4).

### `node:crypto` scryptSync hardcoded in identity domain (ARCH-002, still open)

- Issue: `apps/identity/src/domain/password.ts:9` imports `scryptSync`/`randomBytes`/`timingSafeEqual` from `node:crypto` directly in the domain layer. The manifest declares `engine: "web-worker"` (`apps/identity/src/index.ts:56`), which this code cannot run under.
- Impact: Identity domain is not portable to web/browser runtimes; contradicts the declared runtime engine.
- Fix approach: Define a `PasswordHasherPort` in the domain and move the scrypt implementation to an infrastructure adapter (backlog T-A3).

### SDK `feature()` flag helper is a stub

- Issue: `packages/sdk/src/helpers.ts:169-172` — `feature()` always returns `defaultValue`; there is no flag evaluation, no port call, no LaunchDarkly/memory adapter behind it.
- Impact: Apps using the SDK flag API get silently incorrect behavior (a flag can never be turned on).
- Fix approach: Route through `FeatureFlagsPort` (backlog), or remove the helper until a real implementation exists.

### SDK `ulid()` is not a real ULID

- Issue: `packages/sdk/src/helpers.ts:39-43` — hand-rolled `hexTime + Math.random()` string, uppercase hex, not Crockford base32, not crypto-random. Collides in semantics with the `@mosaix/adapter-id-ulid` adapter (`packages/adapters/id-ulid/src/index.ts`).
- Impact: IDs generated by the SDK helper are neither sortable-by-ULID nor collision-safe at scale; two different "ULID" sources produce incompatible formats.
- Fix approach: Use the real `ulid` package via the `id-ulid` adapter, or `uuidV7()`.

### `messagebus-mosaix` swallows handler errors

- Issue: `packages/adapters/messagebus-mosaix/src/index.ts:10-17` catches handler errors and only `console.error`s them; publish resolves successfully.
- Impact: Silent message loss — no dead-letter, no retry, no surfaced failure. Diverges from `DomainEventBus` in `packages/core/src/event-bus.ts` which has retry + DLQ.
- Fix approach: Emit to a dead-letter queue or rethrow under a configurable policy (documented as "dette identifiée" in `.project/reports/mosaix-packages-responsibilities.md` §9).

### Silent mock fallbacks in production adapters

- Issue: `packages/adapters/featureflags-launchdarkly/src/index.ts:19` defaults `sdkKey` to `"mockKey"`; `packages/adapters/sms-twilio/src/index.ts:17-18` defaults to `ACmock`/`mockToken`; `packages/adapters/email-smtp/src/index.ts:16-18` falls back to `jsonTransport: true` (no-op mock). All accept missing config silently.
- Impact: Misconfigured production wiring silently degrades to a mock instead of failing fast.
- Fix approach: Throw on missing credentials unless an explicit `mock: true` option is passed.

### `cache-redis clear()` flushes the whole database

- Issue: `packages/adapters/cache-redis/src/index.ts:47-49` — `clear()` calls `flushdb()`, wiping every key in the Redis instance, not just the app's keys.
- Impact: One app calling `clear()` destroys other tenants/apps' cached data in a shared Redis.
- Fix approach: Namespace keys per app/tenant and only delete that prefix (e.g. `SCAN`/`DEL` on prefixed keys).

### `crypto-web` contract divergence from `CryptoPort`

- Issue: `packages/adapters/crypto-web/src/index.ts:57-61` returns ciphertext with the GCM auth tag appended (WebCrypto behavior) and omits `tag`; `decrypt()` (lines 64-80) accepts no tag. `crypto-node` (`packages/adapters/crypto-node/src/index.ts`) returns/expects a separate `tag`. Also uses `any` types with `eslint-disable` (lines 1, 7, 9).
- Impact: NodeCrypto ↔ WebCrypto interop is not guaranteed — ciphertext produced by one cannot be reliably decrypted by the other.
- Fix approach: Split the appended tag in `encrypt()` and accept it in `decrypt()` (noted in `.project/dashboard.md` "Qualité adapters (mineur)").

### Ports without adapters (gaps)

- Issue: `event-store`, `logging`, `pubsub` ports have no adapter implementations (per `.project/reports/mosaix-packages-responsibilities.md` §9, "3 ports sans adapter encore").
- Impact: Governance/audit persistence and durable event streams are blocked until `event-store` gets an adapter.

### Runtime composition of ports/adapters not done

- Issue: The 18 ports / 27 adapters are built and unit-tested but **not wired into `RuntimeKernel`** — the kernel still runs `ConsoleLogger`/`InMemoryMetrics`/`InMemoryTracer` and in-memory stores (`.project/dashboard.md` "Points de vigilance": "Socle infra — composition runtime manquante"). Backlog T-I1 (Decision Score 39) is the pending integration.
- Impact: All the adapter infrastructure is currently dead code from the runtime's perspective.

### Manifest `permissions` declarations are decorative

- Issue: `kernel.register()` (`packages/core/src/kernel.ts:289-337`) never reads `manifest.permissions`. The Sales manifest declares `identity:user.lookup:execute:tenant` (`apps/sales/src/index.ts:90-93`) and Identity declares its full permission set (`apps/identity/src/index.ts:132-176`), but nothing validates these declarations against actual grants or uses them.
- Impact: No enforcement that declared permissions match reality; misleading manifests.
- Fix approach: Validate declared permissions against `KernelConfig.grants` at registration, or drop the manifest field.

### Unvalidated schema holes in application manifests

- Issue: `packages/schemas/src/application.ts:27-29` — `navigation`, `layouts`, `widgets` are typed `z.array(z.any())`.
- Impact: Shell/experience manifests carry unvalidated free-form data at the platform boundary.

### Math.random for identifiers

- Issue: `packages/migrations/src/runner.ts:33-35` (`newBatchId`), `packages/adapters/email-ses/src/index.ts:63`, `email-smtp/src/index.ts:37`, `sms-twilio/src/index.ts:31` (messageId fallbacks), `sdk/helpers.ts:41` (`ulid`) all use `Math.random`.
- Impact: Non-crypto identifiers where UUIDs are available; negligible collision risk individually but inconsistent with the platform's `id` port.

## Known Bugs

### `env.boolean` misreads unrecognized strings as `true`

- Symptoms: `packages/config/src/env.ts:39` — `Boolean(val)` fallback means any non-empty string that isn't `true/1/yes/on/false/0/no/off` (e.g. a typo `"falsex"`) evaluates to `true`.
- Files: `packages/config/src/env.ts:34-39`
- Trigger: `env.boolean("FLAG")` with a misspelled env value.
- Workaround: Only use the documented token values.

### `env.string`/`env.number` silently default on missing values

- Symptoms: `packages/config/src/env.ts:8-12` returns `""` and `env.number`/`env.float` return `0` when the variable is absent and no default is given (lines 14-26, 42-54).
- Files: `packages/config/src/env.ts`
- Impact: Misconfiguration is masked (empty string/zero instead of an error), unlike `env.required`/`env.enum` which fail loudly.
- Workaround: Always pass an explicit default or use `env.required`.

### Event store sequence restarts after clear

- Symptoms: `EventStore.append` (`packages/core/src/event-bus.ts:38-47`) assigns `sequence = store.length`; `clear(tenant)` (lines 62-64) deletes the whole per-tenant array, so subsequent appends restart at `0` and `query()` returns duplicates of prior sequence numbers.
- Files: `packages/core/src/event-bus.ts`
- Trigger: `store.clear(tenant)` then new events.
- Impact: Replay/ordering assumptions break; idempotency scan is O(n) per append.

### `sequence` metadata absent from published identity events (ARCH-014)

- Symptoms: `apps/identity/src/application/identity-capabilities.ts:125-138` publishes events with `metadata: { aggregate, aggregateId }` but never a per-aggregate `sequence`.
- Files: `apps/identity/src/application/identity-capabilities.ts`
- Impact: Exact per-aggregate event ordering cannot be reconstructed during distributed replay.

### Kernel start has no crash isolation

- Symptoms: `RuntimeKernel.bootstrap()` (`packages/core/src/kernel.ts:366-379`) initializes apps sequentially; a throwing `initialize()` degrades that app, but a throwing module `initialize()` during `start()` (lines 216-227) flips the whole kernel to `failed` and aborts.
- Files: `packages/core/src/kernel.ts`
- Impact: One misbehaving app/module takes down the ecosystem (T-04 sandbox is backlogged).

### Dry-run reports migrations as "applied"

- Symptoms: `MigrationRunner.run()` with `dryRun: true` (`packages/migrations/src/runner.ts:55-72`) returns `applied`/`rolledBack` populated as if execution happened.
- Files: `packages/migrations/src/runner.ts`
- Impact: Tooling consuming `RunResult` can mistake a preview for a real execution.
- Workaround: Check `options.dryRun` before trusting `applied`/`rolledBack`.

## Security Considerations

### Capability executors receive no caller context

- Risk: `executeCapability` (`packages/core/src/kernel.ts:431-475`) authorizes `callerApp` then invokes `executor(input)` with only the input — the provider cannot see who called or with what tenant-scoped intent beyond the input it was given.
- Files: `packages/core/src/kernel.ts:431-475`, `packages/sdk/src/index.ts:119-124`
- Current mitigation: Authorization happens before the call; tenant is fixed per `MosaixApp`.
- Recommendations: Pass an execution context (`{ callerApp, tenant }`) to executors so providers can enforce finer-grained policy.

### ARCH-012 self-grant — mitigated in SDK, residual risk in manifests

- Risk: The SDK previously auto-granted all manifest permissions (`kernel.grantPermissions(appId, tenant)`). This is now removed: `MosaixApp.register` never grants (`packages/sdk/src/index.ts:59-69`) and grants come only from `KernelConfig.grants` (`packages/core/src/kernel.ts:165-178`).
- Files: `packages/sdk/src/index.ts`, `packages/core/src/kernel.ts`, `demo/identity-sales.ts:25-48`
- Residual: `manifest.permissions` remains unvalidated dead data (see Tech Debt); nothing stops a future commit from reintroducing self-grant.
- Recommendations: Enforce "grant source = kernel config only" as a lint rule/test (e.g. in `demo/identity-sales.test.ts`).

### Synchronous scrypt blocks the event loop

- Risk: `scryptSync` in `apps/identity/src/domain/password.ts:18,26` blocks the Node event loop per hash/verify; a burst of authenticate calls is a CPU-exhaustion/DoS vector on a server.
- Files: `apps/identity/src/domain/password.ts`
- Current mitigation: None (MVP).
- Recommendations: Switch to async `scrypt` (promisified) in the adapter once T-A3 lands.

### No runtime sandbox / worker isolation

- Risk: Manifests declare `engine: "web-worker"` (`apps/identity/src/index.ts:56`, `apps/sales/src/index.ts:40`) but apps run in-process with full kernel access; there is no crash isolation (T-04) or permission-boundary at the process level.
- Files: `packages/core/src/kernel.ts`, `apps/identity/src/index.ts`
- Recommendations: T-04 sandbox is the critical-security backlog item (per `.project/dashboard.md`).

### Mock credentials in production adapters

- Risk: `featureflags-launchdarkly` `"mockKey"`, `sms-twilio` `ACmock`/`mockToken`, `email-smtp` `jsonTransport` — if an app is wired with default config in production, these silently no-op or contact real services with fake credentials.
- Files: `packages/adapters/featureflags-launchdarkly/src/index.ts:19`, `packages/adapters/sms-twilio/src/index.ts:17-18`, `packages/adapters/email-smtp/src/index.ts:16-18`
- Current mitigation: None — fail-open by design.
- Recommendations: Fail closed (throw) when no credentials are supplied (see Tech Debt).

### `storage-local` path traversal

- Risk: `LocalStorageAdapter.getFullPath()` (`packages/adapters/storage-local/src/index.ts:8-10`) does `join(baseDir, path)` with no sanitization — a path containing `../` escapes the base directory.
- Files: `packages/adapters/storage-local/src/index.ts`
- Current mitigation: None.
- Recommendations: Resolve and verify the full path stays within `baseDir` before read/write/delete.

### Secrets only via env

- Risk: `packages/adapters/secrets-env/src/index.ts` reads plaintext `process.env`; no rotation, no encrypted store, no `@mosaix/ports-secrets` production adapter.
- Files: `packages/adapters/secrets-env/src/index.ts`
- Current mitigation: `.env` files are gitignored (`.gitignore` lines 14-15).
- Recommendations: Document as MVP-only; add a managed-secrets adapter before production use.

### In-memory PermissionRegistry — no revocation, no persistence

- Risk: `PermissionRegistry` (`packages/core/src/permission.ts`) is an in-memory append-only list; `deny()` entries exist, but there is no per-app revocation API beyond `clear()` (lines 130-132), and no persistence across restarts.
- Files: `packages/core/src/permission.ts`
- Recommendations: Add revoke API and persist grants via the control plane when it lands.

## Performance Bottlenecks

### Linear scans in hot paths

- Problem: `PermissionRegistry.check()` (`packages/core/src/permission.ts:110-128`) iterates every entry per authorization check — runs on every `publish` and every `executeCapability`. `CapabilityRegistry.resolve()` (`packages/core/src/capability-registry.ts:31-37`) and `EventStore.append()` idempotency (`packages/core/src/event-bus.ts:41`) are O(n) scans.
- Files: `packages/core/src/permission.ts`, `packages/core/src/capability-registry.ts`, `packages/core/src/event-bus.ts`
- Cause: List-based registries chosen for MVP simplicity.
- Improvement path: Index by `(grantedTo, permission, tenant)` and by capability id; use a `Map` keyed by envelope id for the event store.

### Unbounded in-memory growth

- Problem: `EventStore` (`packages/core/src/event-bus.ts:24-65`), `InMemoryCacheWrapper` (`packages/sdk/src/helpers.ts:97-136`), `InMemoryTracer.traces` (`packages/core/src/observability.ts:142-178`), and `InMemoryMetrics` never evict/truncate.
- Files: `packages/core/src/event-bus.ts`, `packages/sdk/src/helpers.ts`, `packages/core/src/observability.ts`
- Cause: No retention policy anywhere.
- Improvement path: Cap sizes (LRU for cache, ring buffer for traces, retention window for event store).

### Synchronous hashing (see Security)

- Problem: `scryptSync` blocks the event loop during `create`/`authenticate`.
- Files: `apps/identity/src/domain/password.ts`
- Improvement path: Async scrypt or native argon2 in the adapter.

## Fragile Areas

### `packages/core/src/kernel.ts` — module facade & ordering

- Files: `packages/core/src/kernel.ts`
- Why fragile: Backward-compat facade (lines 267-284) throws `ServiceNotInstalledError` at access time if a module didn't install; module install order matters (`install()` rejects after `start()`); the `register()` path seeds empty schemas/permissions that later components may or may not validate.
- Safe modification: Add features as new modules, never edit the kernel core (ADR-0002).
- Test coverage: `packages/core/src/kernel.test.ts` (444 lines), `kernel-module.test.ts`, `index.test.ts` — good coverage of lifecycle/state machine.

### `packages/adapters/database-sqlite` — lock/savepoint state machine

- Files: `packages/adapters/database-sqlite/src/index.ts`
- Why fragile: `transaction()` (lines 104-136) tracks `savepointDepth` manually; `acquireMigrationLock()` (lines 138-150) starts `BEGIN EXCLUSIVE` and forces `savepointDepth = 1`, interleaving the lock with the nested-savepoint counter. A lock held across a transaction, or a release outside the runner's `finally` (`packages/migrations/src/runner.ts:97-99`), corrupts the depth accounting.
- Safe modification: Keep lock usage strictly inside the runner's `try/finally`; consider a dedicated lock object instead of reusing the savepoint counter.
- Test coverage: `packages/adapters/database-sqlite/src/index.test.ts` (198 lines).

### `packages/migrations` — checksum/rollback coupling

- Files: `packages/migrations/src/runner.ts`, `registry.ts`, `planner.ts`
- Why fragile: Checksums are computed at load time (`registry.ts:35-46`) and compared against the store on plan; a content change without id bump becomes `MigrationChecksumError` (by design), but the store is `InMemoryMigrationStore` (`packages/migrations/src/store.ts`) — restarting loses applied state, so re-running re-applies everything.
- Safe modification: Always persist via a real store before production; honor R5 (`MigrationMissingError`).
- Test coverage: `packages/migrations/src/index.test.ts` (539 lines), `schema-builder.test.ts` (353 lines).

### Vitest alias bootstrap

- Files: `vitest.config.ts`
- Why fragile: Aliases resolve each `@mosaix/*` to `src/index.ts` entry points explicitly; any new package/port/adapter must be added manually or tests silently resolve from `node_modules` (stale dist). `src/**/*.test.ts` was only added for the shell landing.
- Safe modification: Prefer workspace resolution; keep the alias list in sync with `tsconfig.build.json`.

### `tsconfig.build.json` — 60+ project references

- Files: `tsconfig.build.json`
- Why fragile: Every new port/adapter/app must be registered here **and** in `pnpm-workspace.yaml` **and** in `eslint.config.mjs` element types — three places, easy to miss one (build succeeds, lint or workspace breaks, or vice versa).

### SDK global active-app singleton

- Files: `packages/sdk/src/helpers.ts:14-27`
- Why fragile: `activeAppInstance` is process-global mutable state; `setActiveApp` last-write-wins. Composing multiple `MosaixApp`s in one process makes `logger`/`dispatch`/`execute`/`cache` helpers target whichever app registered last.
- Safe modification: Prefer explicit app references; keep helpers as convenience for single-app processes.
- Test coverage: `packages/sdk/src/index.test.ts` (300 lines) covers registration; helper-global behavior is not covered.

## Scaling Limits

- **Persistence:** Every source of truth is in-memory — `EventStore`, `PermissionRegistry`, `InMemoryUserRepository` (`apps/identity/src/infrastructure/in-memory-user-repository.ts`), `InMemoryMigrationStore`, `InMemoryCacheWrapper`. Restart loses all state.
- **Concurrency:** The SQLite migration lock is `processSafe` only (`packages/adapters/database-sqlite/src/index.ts:76-80`), not distributed; multi-instance migration runs race (PostgreSQL adapter exists but is untested against a real server — `packages/adapters/database-postgres/src/index.ts`).
- **Multi-tenancy:** Tenant scoping exists in the event store key (`packages/core/src/event-bus.ts:27-31`) and permissions, but no tenant isolation at the process level.
- **Scaling path:** T-I1 (runtime composition with real adapters), an `event-store` adapter (durable streams), a persistent `PermissionRegistry`/store, and T-04 sandboxing are the preconditions.

## Dependencies at Risk

### `@aws-sdk/client-s3` / `client-ses` — supply-chain policy block

- Risk: `pnpm install` was blocked by `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` on `@aws-sdk/*@3.1104.0` (`.project/risks/2026-08-06-pnpm-supply-chain.md`, severity Medium, status still "Ouvert").
- Impact: Local `pnpm test`/`check`/`demo` were unexecutable; claimed test counts (207) unverified.
- Current mitigation: `pnpm-workspace.yaml` now lists `minimumReleaseAgeExclude: ["@aws-sdk/*", "@mosaix/*"]` — the risk doc and `.project/dashboard.md` (line 36) predate this and are stale.
- Action: Re-run `pnpm check` and reconcile the risk doc; re-verify the test count (45 test files in `packages/` + `apps/`/`demo`/`src` = 52 files total, versus "207 tests" claimed).

### Node version drift

- Risk: README requires Node 20+, CI pins Node 22 (`.github/workflows/ci.yml:26`), local dev observed on Node 26. `packages/adapters/database-sqlite` relies on `node:sqlite` (`packages/adapters/database-sqlite/src/index.ts:1`), which requires Node 22.5+.
- Impact: Version-sensitive APIs (`node:sqlite`) may behave differently across the supported range.
- Action: Pin the minimum Node version in `package.json` `engines` and align CI.

### Third-party SDKs with mock defaults

- Risk: `launchdarkly-node-server-sdk`, `twilio`, `nodemailer`, `ioredis`, `kafkajs`, `amqplib`, `@elastic/elasticsearch`, `@opentelemetry/api` are pulled by adapters; none have a production integration test (all adapter tests mock the client).
- Impact: A breaking change in any of these SDKs goes undetected until runtime.
- Action: Add at least one smoke/live integration test per critical adapter before production.

## Missing Critical Features

- **Runtime composition (T-I1):** adapters never wired into the kernel — the entire adapter layer is currently inert.
- **Capability I/O validation (T-A5):** capability boundary accepts arbitrary data.
- **Permission grant revocation & persistence:** grants are append-only in-memory.
- **Event-store adapter:** no durable event streams (blocks audit/governance).
- **Crash isolation (T-04):** no sandbox — a failing app can take down the kernel.
- **CI activation:** `.github/workflows/ci.yml` exists but the remote (`https://github.com/Cheteck/devFlow.git`) was configured after the workflow was written; CI has never validated a build. The current branch is a temporary generated name (`jules-6253545875516503602-915c0284`) with uncommitted work (`src/`, `.project/` files untracked) — the repository has never had a clean `main`-based validated run.
